# 혼자서 모드 설계

작성일: 2026-08-05
상태: 구조와 경제 수치 확정. 강화 수치 표기와 보관함 UI 만 남음

## 배경

지금 이 앱은 카드팩을 열고 뽑은 카드로 대결하는 party 게임 하나뿐이다. 여기에
**경제가 도는 혼자서 모드**를 새로 판다. 크레딧으로 팩을 사고, 카드를 팔고, 강화해서
자랑하는 데까지가 이번 범위다.

모드 이름은 아직 정하지 않았다. 이 문서와 코드에서는 임시로 `solo`(혼자서) /
`multi`(여럿이서)로 부른다.

## 배포 범위와 라이선스 판단

**개인 웹 프로젝트로 계속 간다.** 실명·선수 사진·팀 로고를 지금 그대로 쓴다.
앱인토스나 앱스토어 배포는 하지 않는다.

이렇게 정한 근거를 남겨둔다. 나중에 배포 얘기가 다시 나오면 여기부터 읽으면 된다.

- **절차**: 앱인토스는 게임 등록 전에 게임제작업 등록과 게임물 등급분류를 요구한다.
  귀찮지만 막히는 벽은 아니다.
- **확률형 아이템 확률 공개**: 유상 구매 아이템만 대상이다. 크레딧을 현금으로 팔지
  않으므로 해당 없고, 연매출 1억 미만이면 애초에 표시 의무자에서 빠진다. 지금도
  `(?)` 툴팁에 등급 확률을 다 적고 있어 사실상 충족한다.
- **팀 로고**: 상표 + 저작권. KBOP와 프리미어리그 소유다. 변명 여지가 없다.
- **선수 사진**: 촬영자 저작권 + 초상권. 게다가 네이버 pstatic 과 FotMob CDN 을 그대로
  핫링크하고 있어 트래픽까지 남의 것이다.
- **실명**: 2006년 이종범 외 122명 소송에서 법원이 게임에 선수 이름 쓰는 것을 막았고,
  이후 KBOP 가 선수협에 라이선스 수익 30% 를 주는 구조가 굳었다. 게임에 실명을 쓰려면
  라이선스가 필요하다는 것이 업계 기준이다.
- **기록 자체**는 사실이라 저작권 대상이 아니다. 다만 네이버·FotMob 에서 긁는 것은
  데이터베이스제작자 권리와 이용약관 문제가 따로 붙는다.

노출도가 리스크를 결정한다. 개인 링크로 굴리면 현실적으로 문제되지 않지만, 토스 앱
안이나 앱스토어에 올리는 순간 성격이 달라진다. 올릴 거면 사진과 로고는 반드시 빼야
하고, 실명도 라이선스 없이는 위험하다.

## 게임 루프

```
시작: 크레딧 N 지급
  ↓
상점  가격이 다르면 확률표도 다른 팩을 고른다
  ↓
개봉  기존 카드깡 연출을 그대로 쓴다 (팩 뜯기 → 카드 뒤집기)
  ↓
보관함에 카드가 쌓인다
  ↓
보관함에서 고른다
  · 판매 → 크레딧 회수
  · 강화 → 성공(+1) / 실패(단계 유지) / 파괴(소멸)
           파괴 보호권을 켜면 값이 비싸지는 대신 파괴가 사라진다
  ↓
크레딧이 남으면 상점으로
  ↓
끝  파산(강제) 또는 "여기까지 하고 결과 보기"(자발적)
  ↓
결과  이 런에서 도달한 최고 카드 + 자랑 링크
```

**목표는 "최고의 한 장"이다.** 고정된 시작 크레딧으로 출발해 가장 높이 강화한 카드를
남기는 것이 이 런의 성과다. 무한히 도는 루프에는 성취감이 남을 자리가 없어서
파산이라는 끝과 최고 기록이라는 결과물을 같이 뒀다.

**파산 판정은 `크레딧 < 최저 팩 가격 && 보관함이 비었음` 하나뿐이다.** 보관함에 카드가
남아 있으면 팔아서 계속할 수 있으니 아직 끝이 아니고, 다 팔았는데도 팩 값이 안 되면
그때 끝난다. 조건이 하나라 판정이 애매할 여지가 없다.

**끝나는 방법은 두 가지다.** 파산은 강제 종료고, "여기까지 하고 결과 보기"는 자발적
종료다. 파산만 끝이면 수십 번의 클릭이 남은 판에 갇힌다. 이 게임의 본질은 강화를 잘
해보는 것이지 파산까지 버티는 게 아니다.

**최고 기록은 런 내내 따로 들고 간다.** 카드가 강화 중에 터져도 "+7까지 갔었다"는
기록은 남아야 자랑거리가 된다.

**성과는 강화 수치가 아니라 카드 가치(등급 × 강화 배수)로 잰다.** 강화 수치만 보면
커먼을 싸게 여러 장 태우는 게 최적 전략이 되어 레전드를 강화할 이유가 사라진다.

**강화 수치의 기본값은 0이고 표시하지 않는다.** `+1` 부터 카드에 붙는다. 던파·메이플
방식이다. 피파는 기본이 1강이지만, 우리 카드는 왼쪽 위에 이미 등급 배지가 붙어 카드의
격을 말하고 있어서 "1강"까지 붙이면 격을 나타내는 표시가 둘이 되어 서로 싸운다. 팩에서
나온 카드가 압도적으로 많으므로 그 다수에 아무 표시가 없어야 강화한 소수가 튄다.

강화는 시도마다 성공·실패·파괴가 확률로 갈린다. 세 갈래가 모든 단계에서 동작하고,
실패는 그 단계를 유지하는 것으로 본다(재화만 잃는다).

**파괴 보호권**은 강화 버튼 아래 토글이다. 켜면 값이 비싸지는 대신 파괴가 사라지고,
실패해도 단계가 유지된다. 성공률은 그대로이므로 남은 확률이 전부 실패로 흡수된다.

## 라우팅과 화면

시즌은 종목 안에 들어간다. 종목은 안 늘지만 시즌은 매년 늘어나므로, 시즌을 첫 화면에
두면 메인이 계속 부푼다.

```
/                          메인. 종목 2 × 모드 2 = 4칸
/kbo/solo                  시즌 고르기
/kbo/solo/2026             혼자서 게임
/kbo/multi                 시즌 고르기
/kbo/multi/2026            여럿이서 게임
/kbo/flex/...              자랑 링크
```

시즌 선택 화면은 항목이 하나여도 보여준다. PL 26/27 이 곧 개막하고 KBO 도 시즌이
끝나면 다음 해에 2026 이 남는다. 시즌이 하나인 상태는 지금 이 순간뿐이라 "하나면
건너뛴다" 분기를 넣을 이유가 없다. 그 화면이 LIVE 가 무슨 뜻인지 설명할 자리도 된다.

### 메인화면

```
카드깡

  혼자서
  주어진 돈으로 카드팩을 사고 카드깡을 한 뒤 선수를 강화해봐요
  [ ⚾ KBO  LIVE ]   [ ⚽ PL ]

  여럿이서
  친구들과 함께 카드깡하고, 뽑은 카드로 대결해요
  [ ⚾ KBO  LIVE ]   [ ⚽ PL ]
```

시즌 라벨이 안으로 들어갔으니 종목 카드에서는 엠블럼이 주인공이 된다. 지금 `2026`,
`25/26` 을 크게 띄우던 자리다.

LIVE 배지는 **그 종목에 라이브 시즌이 하나라도 있으면** 붙는다. 매니페스트에서
계산하므로 26/27 PL 을 추가하면 PL 카드에도 자동으로 붙고, KBO 시즌이 끝나
`live: false` 가 되면 자동으로 떨어진다.

### 시즌 선택 화면

```
KBO · 혼자서

  [ 2026        LIVE ]   매일 기록이 갱신돼요. 어제보다 오른 선수는 카드에 ▲가 붙어요
  [ 2025            ]    시즌이 끝나 등급이 고정된 카드예요
```

## 데이터 파이프라인

지금은 페이지를 열 때마다 서버가 네이버·FotMob 을 찌르고 카드를 만든다(`revalidate = 3600`).
이걸 뒤집어서 **깃액션이 하루 한 번 카드를 다 구워 저장소에 커밋**하고, 앱은 그 JSON 을
읽기만 한다.

```
.github/workflows/daily.yml   매일 1회 (KBO 경기가 끝난 뒤, 새벽)
  └ scripts/snapshot.ts
      1. 기존 data/kbo-2026.json 을 읽어 어제 등급을 기억한다
      2. getKboPool() 을 호출한다 (지금 있는 그 함수 그대로)
      3. 어제와 등급이 다른 카드에만 prevTier 를 박는다
      4. data/kbo-2026.json 에 덮어쓰고 커밋한다 → Vercel 재배포
```

액션은 매니페스트에서 `live: true` 인 시즌만 돈다.

저장하는 것은 raw 응답이 아니라 **완성된 `Card[]`** 다. 그래야 앱 쪽 page 가 JSON 을
읽는 한 줄로 끝나고, 등급 변동도 파일 하나 안에서 처리된다. 비교용 별도 파일이 필요 없다.

부수 효과가 좋다. 네이버·FotMob 호출이 하루 한 번으로 줄어 차단 위험이 낮아지고,
런타임 fetch 실패가 사라진다. 액션이 실패하면 커밋이 안 되므로 어제 데이터로 계속
돌아간다. 지금 page 에 있는 "기록을 못 가져왔어요" 화면은 사실상 안 쓰이게 된다.

### DB 를 쓰지 않는 이유

끝난 시즌을 영구 보존해야 하니 DB 가 필요해 보이지만, 저장소가 이미 그 일을 한다.
끝난 시즌의 카드 풀은 130KB 짜리 JSON 한 덩어리고 한 번 굳으면 다시 안 바뀐다.

```
data/
  kbo-2026.json     라이브. 액션이 매일 덮어쓴다
  epl-2526.json     확정. 한 번 굽고 다시 안 건드린다
  epl-2627.json     개막하면 추가, 라이브로 시작
```

시즌이 끝나면 액션 대상에서 빼기만 하면 파일이 그 자리에 굳는다. 마이그레이션도
백업도 스키마 관리도 없다. 10년을 쌓아도 20개 파일에 2.6MB다.

- 인프라도 비용도 0이고, 연결 문자열 없이 로컬에서 그대로 재현된다
- `git log data/kbo-2026.json` 이 등급 변동 히스토리를 공짜로 준다
- 코드와 데이터가 같은 커밋이라 배포가 원자적이다

DB 가 필요해지는 조건은 따로 있다. 사용자별 데이터를 서버에 두거나, 전체 순위표를
만들거나, 쓰기가 잦을 때다. 보관함은 localStorage 에 두고, 순위표는 만들지 않고,
쓰기는 하루 한 번이라 셋 다 해당 없다. 나중에 순위표를 붙이고 싶어지면 그때 사용자
기록 테이블 하나만 얹으면 되고, 카드 풀은 정적 데이터라 영영 DB 에 넣을 이유가 없다.

시즌 종료 판정은 손으로 한다. 1년에 두 번 있는 일이고 `live: false` 한 글자면 끝난다.

### 매니페스트

```ts
// app/_sports/seasons.ts — 메타데이터만. 클라이언트에서 읽어도 안전하다
export type Season = {
  id: string;      // URL 세그먼트로 그대로 쓴다
  sport: "kbo" | "epl";
  label: string;   // 화면 표기
  live: boolean;   // 깃액션이 매일 갱신하는 대상인가
};

export const SEASONS: Season[] = [
  { id: "2026", sport: "kbo", label: "2026", live: true },
  { id: "2526", sport: "epl", label: "25/26", live: false },
];
```

```ts
// app/_sports/pools.ts — 서버 전용. JSON 로더를 여기 모은다
export const POOLS = {
  "kbo-2026": () => import("../../data/kbo-2026.json"),
  "epl-2526": () => import("../../data/epl-2526.json"),
};
```

두 파일로 나누는 이유는 메인화면이 시즌 목록을 그릴 때 JSON 로더가 딸려오면 130KB 짜리
데이터가 브라우저 번들에 섞일 위험이 있어서다. 메타데이터와 로더를 갈라두면 그럴 일이 없다.

시즌 하나를 추가할 때 손대는 곳은 이 두 파일에 한 줄씩과 `data/` 에 JSON 하나다.

### 등급 변동 표시

`Card` 에 `prevTier?: TierKey` 한 칸을 더한다. **등급이 실제로 바뀐 카드에만** 넣고
그대로면 넣지 않는다. 앱에서는 `card.prevTier` 가 있으면 오른 건지 내린 건지 화살표를
그린다.

라이브 시즌은 보유 카드의 등급이 움직인다. 어제 EPIC 이던 카드가 오늘 RARE 로
내려가면 판매가도 같이 떨어진다. 이걸 버그가 아니라 **라이브 모드만의 규칙으로 내세운다.**
"오늘 잘한 선수는 내일 값이 오른다"가 성립하면 안 팔고 쥐고 있을 이유가 생기고,
시즌이 끝나 값이 고정된 모드와 확실히 다른 게임이 된다.

### 최소 출전 커트 고정

팀 경기수에 비례하던 커트를 상수로 굳힌다.

| | 지금 (동적) | 고정 후 |
|---|---|---|
| 타자 | 경기수 × 1.2 | 124타석 |
| 선발 | 경기수 × 0.3 | 31이닝 |
| 불펜 | 경기수 × 0.2 | 21이닝 |

2026-08-05 기준 팀 경기수 103 을 곱해서 나온 값이다. 경기수 상위 분포가
103·101·101·101·100 이라 최다 출전이 이상치가 아닌 것도 확인했다.

여기서 딸려오는 게 크다. 커트가 동적이면 시즌이 갈수록 기준이 올라가서 보관함에 있던
선수가 다음에 열었을 때 풀에서 빠질 수 있다. **커트를 고정하면 그게 거의 사라진다.**
누적 기록은 줄지 않으므로 한 번 커트를 넘은 선수는 부상으로 시즌을 접어도 계속 풀에
남는다. 방출이나 은퇴로 응답에서 행 자체가 빠지는 경우만 남는데 드물다.

## 저장

런 상태는 localStorage 에 둔다. 서버도 DB 도 로그인도 없다.

```ts
type Run = {
  v: 1;                                       // 스키마 버전
  season: string;                             // "kbo-2026"
  credits: number;
  vault: { id: string; plus: number }[];
  best: { id: string; plus: number } | null;  // 이 런의 최고 기록
  over: boolean;
};
```

카드 전체가 아니라 **선수 id 와 강화 수치만** 저장한다. 카드 데이터는 저장소의 JSON 에
있으므로 id 로 찾아 복원하면 항상 최신 성적으로 살아난다. 저장 용량도 몇백 바이트로 끝난다.

복원되지 않는 id 는 보관함에서 조용히 빼고 크레딧 보상은 하지 않는다. 커트 고정으로
거의 일어나지 않는 일이라 판정을 단순하게 두고, 왜 그런지는 주석으로 남긴다.

## 자랑 링크

최종 카드만 주소로 만들어 공유한다. 받는 쪽은 그 주소로 카드를 복원하고,
`opengraph-image.tsx` 가 그 카드를 PNG 로 굽는다. 카톡에 붙이면 카드가 그대로 뜬다.

`ImageResponse`(`next/og`)가 Next 16 에 내장돼 있어 새 의존성이 없다.

**`opengraph-image.tsx` 는 `params` 만 받고 `searchParams` 는 받지 않는다.** 그래서
공유 상태는 쿼리가 아니라 경로에 넣어야 한다. catch-all 세그먼트를 쓴다.

```
app/[sport]/flex/[...code]/page.tsx
app/[sport]/flex/[...code]/opengraph-image.tsx

/kbo/flex/2026/타자-12345/7    →  code = ["2026", "타자-12345", "7"]
```

세그먼트를 나누는 이유는 KBO 카드 id 가 `타자-12345` 처럼 하이픈을 품고 있어서
하나의 문자열로 이어 붙이면 구분자가 충돌하기 때문이다.

URL 을 고쳐 `+99` 를 위조할 수 있지만 전체 순위표가 없으므로 위조할 이유도 없다.

스크립트로 옮겨갈 뿐이고 기존 테스트도 그대로 살아 있다.

### Next 16 확인 사항

- `params` 는 Promise 다. `await` 해야 한다
- `generateStaticParams` 로 시즌 경로를 빌드 때 미리 굽는다. `dynamicParams = false` 를
  걸면 없는 시즌 주소는 404 가 된다
- 자랑 링크는 조합이 무한하므로 정적 생성 대상이 아니다

### 기존 코드에서 손대는 곳

세 군데뿐이다.

1. **`game.tsx` 에서 `PackShell` 을 꺼내 `_game/pack.tsx` 로 옮긴다.** 혼자서 모드도 팩을
   뜯는데 지금은 1103줄짜리 컴포넌트 안에 박혀 있어 못 쓴다. 옮기기만 하고 내용은 안 바꾼다.
2. **`card.tsx` 의 `PlayerCard` 에 `plus?: number` prop 을 더한다.** 값이 있을 때만 `+7`
   을 얹는다. 기존 호출부는 한 줄도 안 건드려도 되고, 강화 수치를 `Card` 타입에 섞지
   않아 기존 모드 쪽 타입이 더러워지지 않는다. `card.tsx` 는 등급 5종 × 크기 3종을 한
   컴포넌트가 그리므로 `mini` 에서 `+7` 이 이름을 밀어내지 않는지 따로 확인한다.
3. **`kbo.ts` 의 최소 출전 커트를 상수로 바꾼다.** 위의 고정값을 쓴다.

옛 경로 `/kbo`, `/epl` 은 `next.config.ts` 의 `redirects()` 로 `/kbo/multi` 에
흘려보낸다. 파일을 안 만들어도 되고 라우트 충돌도 없다.

## 경제 수치

전부 `economy.ts` 한 곳에 상수로 모은다. 아래 값은 시뮬레이션으로 파탄만 걸러낸
출발점이고, 미세 조정은 실제로 눌러보면서 한다.

### 시작 크레딧 2,000

1,000 으로도 해봤지만 짧았다. 카드 값에 비해 자본이 작아 레전드 하나를 강화하면(900)
자본의 절반이 날아가고, 팩을 13번밖에 못 산다.

### 판매가

| 커먼 | 언커먼 | 레어 | 에픽 | 레전드 |
|---|---|---|---|---|
| 20 | 80 | 250 | 800 | 3,000 |

**카드 가치 = 기본가 × 1.6^강화수치.** 이 값이 곧 판매가이자 성과 점수다.

레전드를 에픽의 3.75배로 벌린 이유가 있다. 등급 점수 비율(100 대 45)을 그대로 쓰면
플래티넘 팩 값의 절반이 레전드 한 장이 되어, 팩 값을 맞추려면 레전드가 70% 확률로
나와야 한다. 그러면 "레전드 포함"이 광고가 아니라 보장이 되어버린다.

### 팩

| 팩 | 가격 | 장수 | 레전드 | 에픽 | 레어 | 언커먼 | 커먼 | 엣지 | 레전드 들었을 확률 |
|---|---|---|---|---|---|---|---|---|---|
| 일반 선수팩 | 400 | 3 | 1% | 4% | 17% | 26% | 52% | −1.8% | 3% |
| 고급 선수팩 | 1,200 | 5 | 2% | 9% | 26% | 48% | 15% | 0.7% | 10% |
| 플래티넘 선수팩 | 3,000 | 5 | 9% | 23% | 40% | 28% | 0% | 3.9% | 38% |

구매 유도 문구:

- 일반 선수팩 · 부담 없이 한 봉. 레전드 3%
- 고급 선수팩 · 커먼 비율을 15%까지 낮췄어요. 레전드 10%
- 플래티넘 선수팩 · 커먼이 안 나와요. 레전드 선수 등장 38%!

시작 2,000 이면 일반팩 5개나 고급팩 1개를 살 수 있고 **플래티넘(3,000)은 못 산다.**
첫 화면부터 "잘게 여러 번 대 한 번에 좋은 것"이라는 고민이 생기고, 플래티넘은 모아야
닿는 목표로 남는다.

**일반팩만 엣지가 마이너스인 것은 의도다.** 하우스 엣지가 있으면 크레딧이 계속 깎여서
"모아서 고급팩 산다"가 운에만 달리게 된다. 느리지만 확실히 모으는 길을 열어두고,
하우스는 플래티넘과 강화에서만 가져간다.

### 강화 확률

`성공률 = 95, 85, 70, 55, 40, 25, 16, 10, 7, 5` (%), 나머지가 실패와 파괴다.
천장은 +10 이다.

| 목표 | 성공 | 실패 | 파괴 | 누적 도달률 | 가치 배수 |
|---|---|---|---|---|---|
| +1 | 95% | 4% | 1% | 99.0% | 1.6× |
| +2 | 85% | 12% | 3% | 95.6% | 2.6× |
| +3 | 70% | 23% | 7% | 86.9% | 4.1× |
| +4 | 55% | 33% | 12% | 71.3% | 6.6× |
| +5 | 40% | 42% | 18% | 49.2% | 10.5× |
| +6 | 25% | 50% | 25% | 24.6% | 16.8× |
| +7 | 16% | 54% | 30% | 8.6% | 26.8× |
| +8 | 10% | 56% | 34% | 1.9% | 42.9× |
| +9 | 7% | 56% | 37% | 0.31% | 68.7× |
| +10 | 5% | 55% | 40% | 0.03% | 110× |

피파 온라인 곡선을 참고했다. 초반은 후하게 주고 +6 에서 절벽을 만들고 그 뒤는 길게
끈다. 선형 곡선도 해봤지만 실패율이 낮아 같은 단계를 계속 두드리게 되어 강화 클릭이
두 배로 늘었다. 절벽 곡선은 파괴가 일찍 정리해줘서 판이 빠르다.

누적 도달률은 크레딧이 무한하다고 쳤을 때다. 실제로는 돈이 먼저 떨어진다.

### 강화 비용과 보호권

**강화비 = 현재 카드 가치 × 30%**
**보호료 = 현재 카드 가치 × 파괴율 × 1.3** (강화비에 더해서 낸다)

| 도전 | 카드 가치 | 강화비 | 보호 켰을 때 | 배수 |
|---|---|---|---|---|
| +0→+1 | 3,000 | 900 | 939 | 1.0× |
| +3→+4 | 12,288 | 3,686 | 5,603 | 1.5× |
| +5→+6 | 31,457 | 9,437 | 19,661 | 2.1× |
| +7→+8 | 80,531 | 24,159 | 59,754 | 2.5× |
| +9→+10 | 206,158 | 61,847 | 169,049 | 2.7× |

강화비를 **기본가에 선형**(`기본가 × (0.4 + 0.2N)`)으로 두는 안도 해봤는데 버렸다.
고강화로 갈수록 카드 가치 대비 강화비가 40% 에서 3% 로 떨어져 상대적으로 공짜가 된다.
현재 가치 비례로 바꾸니 경제가 건강해졌다. 다만 비율을 20% 로 낮추면 +5 까지 올려
파는 것이 돈벌이가 되어 경제가 폭주한다(시뮬에서 팩 3,097회, 크레딧 46만). 30% 가 선이다.

보호료도 처음에는 강화비의 배수(`강화비 × (1 + 파괴율 × 10)`)로 잡았다가 버렸다.
강화비가 이미 카드 가치의 30% 이므로 거기에 5배를 곱하면 보호권이 카드 가치의 150%가
되어 카드보다 비싸진다. 시뮬에서 보호 사용이 판당 2회에 그쳤다. **파괴로 잃을 금액
기준으로 매기는 것이 맞다.** 기대손실보다 30% 비싸게 받아 "안전을 웃돈 주고 산다"가
성립한다.

### 검증 결과 (시작 2,000, 3,000회)

| 전략 | 팩 | 강화(보호) | 중앙값 | 상위 10% | 최대 | 플래티넘 도달 |
|---|---|---|---|---|---|---|
| 강화 안 함 | 24 | 0 | 800 | 3,000 | 3,000 | 44% |
| 에픽+ 무한, 보호 안 씀 | 27 | 39(0) | 3,000 | 19,661 | 50,332 | 57% |
| 에픽+ 무한, +4부터 보호 | 39 | 69(6) | 3,000 | 19,661 | 31,457 | 57% |
| 에픽+ 무한, 항상 보호 | 61 | 102(102) | 3,000 | 19,661 | 31,457 | 57% |

보호를 안 쓰면 최대가 50,332(레전드 +6)까지 열리고, 켜면 31,457 에서 막히는 대신
오래 버틴다. 안전과 한방이 갈린다. 판 길이는 팩 27~61회에 강화 39~102회로 20분 안팎이다.

강화를 아예 안 하면 천장이 레전드 한 장(3,000)에 막혀 편차가 사라진다. 강화가 없으면
성취감이 없다는 판단이 숫자로 확인된 셈이다.

시뮬레이션 전략은 "에픽 이상이면 무조건 강화" 같은 무지성 규칙이라 사람의 판단을
흉내내지 못한다. 경제 폭주나 장치 사망 같은 파탄을 걸러내는 용도로만 썼다.

## 아직 안 정한 것

**강화 수치를 카드 어디에 어떻게 표시할지.** 이름 옆에 `+7` 텍스트만 붙일지, 등급 배지
안에 넣을지, 수치에 따라 색을 바꿀지. 피파는 강화 등급마다 색이 다른데 우리는 이미
등급마다 색이 있어서(`STYLE[tier]`) 충돌할 여지가 있다.

**보관함 UI.** 카드가 수십 장 쌓이는데 목록을 어떻게 보여주고 판매·강화를 어디서
누르게 할지.

둘 다 눈으로 봐야 정할 수 있는 문제라 화면을 그려보고 결정한다.

## 테스트

`economy.ts` 는 순수 함수만 두므로 `node --test` 로 전부 덮는다. 기존 `deck.test.ts`,
`battle.test.ts` 와 같은 방식이다.

- 팩 세 종의 확률표 합이 각각 100% 인지
- 팩 가격이 기대 회수보다 크게 어긋나지 않는지(엣지가 의도한 범위인지)

- 강화 확률(성공·실패·파괴)의 합이 각 단계에서 100% 인지
- 보호권을 켜면 파괴 확률이 0 이 되고 그만큼 실패로 넘어가는지
- 보호권 값이 어느 단계에서도 카드 가치를 넘지 않는지
- 파산 판정이 경계값에서 맞는지 (크레딧이 최저 팩 가격과 같을 때, 보관함이 빌 때)
